# PDF-to-Markdown Paygate: operator notes (not a deployment runbook)

The app is NOT deployed by these notes. Disposable-DB SQL smoke and two-session concurrency checks have passed; paid UI and production traffic still require Stripe test-mode delivery, ingress checks, app-role startup verification, and explicit production approval.

## Ingress and routes
- The Node server defaults to `127.0.0.1:3001`; terminate TLS at a trusted ingress and block direct public access to Node. Set `TRUSTED_PROXY_IP` to the verified socket peer of that ingress. The ingress must overwrite (not append or preserve) `CF-Connecting-IP`. Test spoofed, duplicate, malformed and absent headers before release.
- User routes: `POST /v1/convert`, `GET /v1/quota`, `POST /v1/checkout`, `GET /v1/checkout-status?session_id=...`, `POST /v1/redeem`. User POSTs require an exact `Origin` matching `PUBLIC_BASE_URL`; identity is a signed `HttpOnly; Secure; SameSite=Lax` cookie. Do not redirect or rewrite the paths without an explicit tested mapping.
- Stripe webhook: `POST /v1/stripe/webhook`; it must receive the unmodified raw request body and `Stripe-Signature` header. It intentionally has no browser cookie/Origin requirement. Configure and verify the Stripe endpoint/events in test mode first; a webhook signature is required before DB/provider side effects.

## App-only configuration
The Node process reads its environment; it does NOT automatically load `~/.hermes/.env` or an arbitrary project `.env`. Supply a private app-only environment via the deployment supervisor/secret manager; never mount `/opt/paygate/.env` (it contains the DB superuser password), and never commit secrets. The startup requires `API_TOKEN`, `PAYGATE_DATABASE_URL` (user `paygate_pdf2md`, database `paygate`), `PAYGATE_IP_SECRET`, `PAYGATE_CODE_SECRET`, `PAYGATE_COOKIE_SECRET`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_ID`, `PUBLIC_BASE_URL` (HTTPS origin), and `TRUSTED_PROXY_IP`. Optional: `API_URL`, `HOST`, `PORT`. The three independent paygate secrets must be random and distinct. Verify the DB role and seeded price/product with the same Stripe mode used by Checkout; no live charges during setup.

## SQL operator gates
On an operator-approved paygate database, apply the handoff's base schema and `pdf2md` seed, then `pdf_to_markdown/sql/020_checkout_status.sql`, `pdf_to_markdown/sql/025_pdf2md_guards.sql`, and **mandatory** `pdf_to_markdown/sql/030_pdf2md_scoped_quota.sql` in that order. Apply 030 before starting the app: it revokes the role's app-ID-taking quota/consume functions and grants only `quota_pdf2md(subject,ip)`, `consume_pdf2md_free(subject,ip)`, and `consume_pdf2md_paid(subject)`. Startup fails closed when any generic grant remains or any scoped grant is absent. Run `920_checkout_status_test.sql` and `925_pdf2md_guards_test.sql` with `psql -v ON_ERROR_STOP=1` and confirm notices and rollback; 925 creates a second app inside its rollback-only transaction and probes all generic functions under `SET ROLE paygate_pdf2md`. Base/seed/020/025/030 and both 920/925 tests passed on the authorized disposable `paygate-db` on 127.0.0.1:5437. A separate two-session same-PI test passed in both orders: fulfillment then reversal revoked the pass, and reversal then fulfillment returned NULL without a purchase. This is not a production migration or a real Stripe delivery test. Set the dedicated DB role password out of band; never copy a `paygate_app` or superuser URL into the PDF app.

## Maintenance
Investigate Stripe delivery retries, refund/dispute mismatches, and coded anomalies; keep personal data out of alerts.

## Recovery secret and reversal monitoring
- `PAYGATE_CODE_SECRET` (the configured code secret) deterministically derives restore codes from Checkout session IDs. Keep it in the secret manager, not logs, Git or database; retain protected historical versions and backups for the lifetime of redeemable passes. Rotating or losing it without a migration/recovery plan changes the derived code and can prevent existing buyers from recovering/redeeming their passes. Plan rotation with an expiry/compatibility window and a verified customer recovery procedure; restrict and audit access to old versions.
- Monitor the restricted `paygate.pdf2md_webhook_anomalies` table by reason and count, plus webhook 5xx/retry backlog and unresolved delivery failures. Investigate spikes or persistent `invalid_provider_shape`, `price_mismatch`, `metadata_mismatch`, or `missing_email`; do not put raw event IDs, emails or payloads in alerts. Reconcile provider charge/PI amounts, currency and identity against purchases and tombstones before manual remediation.
- Reversal policy: a signed charge event is actionable only when its re-fetched charge matches the scoped PI and its **expanded latest charge** identity, and both are the €2/EUR product. A historical charge that is no longer latest, or missing/string/mismatched `latest_charge`, cannot be safely resolved by this handler: return retryable 503 and escalate persistent retries for provider investigation; never acknowledge or tombstone on an uncertain identity. Checkout pre/post checks likewise retry on uncertain provider state. This can require operator intervention if the latest charge has permanently changed.
- SQL guard smoke 920/925 and two-session same-PI concurrency tests passed on the authorized disposable database. Real Stripe test-mode delivery, ingress verification, app-role startup, and production migration/deployment have **not** been run here.
