# PDF to Markdown Donation Modal + Stripe Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` task by task. Track checkboxes; each code task follows RED → GREEN → commit. This document is a plan, not authorization to deploy or charge live cards.

**Goal:** Enable one-time, voluntary EUR support payments from the existing PDF-to-Markdown Donate button through an accessible DE/EN modal and Stripe-hosted Checkout, without PayPal integration.

**Architecture:** Keep amount selection and Marco's explanation in the React modal; create Checkout Sessions server-side using Stripe's REST API and inline `price_data.product_data`, so no pre-created Dashboard Product/Price is needed. A shared ESM payment module is called by a Cloudflare Pages Function (the deployed static site) and the existing Node server (local hosting); a read-only session-status endpoint verifies returns against Stripe before showing a paid confirmation. Do not couple donations to PDF uploads or introduce a database, subscription, webhook, or Stripe.js for this one-off, no-fulfillment flow.

**Tech stack:** React 19/CRA/Jest/Testing Library, Node built-in HTTP + node:test, Cloudflare Pages Functions, fetch + Stripe Checkout REST. Workspace/repo root: `/root/repo/pdf_to_markdown`; all paths below are relative to it.

**Design baseline:** User specified Stripe, one-time donation modal, German/English recipient copy and no PayPal; prior discussion recommended hosted checkout over embedding a payment form. This plan is the approved direction implied by the explicit implementation request; no separate spec file is being edited in plan mode.

## Global constraints

- Price and currency set on the server, never trust a client price or checkout URL; only validated integer `amountCents` 500–50000 divisible by 100, and `locale` exactly `de` or `en`.
- Set `mode=payment`, `currency=eur`, `quantity=1`, `locale=de|en`, `price_data.product_data.name=Voluntary support for Marco Rudolph` (English; no invented charitable status), `metadata[donation_context]=pdf_to_markdown`, `client_reference_id` omitted; Stripe dynamically selects enabled eligible payment methods. No `payment_method_types=['card']` restriction and no PayPal integration. On status lookup, require that metadata marker too, so another same-account Checkout Session cannot masquerade as a donation.
- Return only `{url}` for a successful checkout creation; only accept a returned Stripe `https://checkout.stripe.com/...` URL. Return generic error text without Stripe secrets/response body. Never send PDF content, file name, or unrelated personal data to Stripe.
- Success URL is `${DONATION_ORIGIN}/?donation=success&session_id={CHECKOUT_SESSION_ID}` and cancel URL `${DONATION_ORIGIN}/?donation=cancel`. A return URL alone is **not proof of payment**; GET status asks Stripe, and confirms only `payment_status === 'paid'`, `mode === 'payment'`, `currency === 'eur'`, amount in supported range and matching metadata. Map `status=open` to `incomplete`, `status=complete` + `payment_status=unpaid` to `processing`, `status=expired` to `expired`; invalid/not-found to `not_found`. Never claim successful payment for `processing`.
- Require exact same-origin `Origin` on checkout POST as **browser CSRF mitigation only**, not bot authentication: scripts can spoof Origin. Accept JSON only; cap body at 1024 bytes. In the browser, prevent double-submit with a synchronous ref-based in-flight guard. Disable caching and set `Referrer-Policy: no-referrer` on payment APIs; do not log payment identifiers or provider responses. Normalize a configured trailing `/` and validate `DONATION_ORIGIN` as an origin-only URL: HTTPS outside localhost/127.0.0.1; never derive it from request Host.
- Preserve existing upload, legal routes, CSP, responsive design and token styles; no redirect merely from opening the modal. Use native `<dialog>.showModal()` (focus management + Escape), visible close control, `aria-labelledby`, return focus to Donate trigger.
- Default-off build flag `REACT_APP_DONATIONS_ENABLED=1` enables the Donate button; all other values retain a disabled/unavailable control. Work on a feature branch (not the auto-deployed `main`); test-mode Preview can be smoke-tested with a separate explicitly configured preview origin if needed, but the default preview build stays off. Before merging/enabling in production, deploy Functions and set `STRIPE_SECRET_KEY`, `DONATION_ORIGIN`, Cloudflare rate limit and Stripe Radar controls; then build with the flag enabled and smoke-test atomically. No live Stripe configuration changes in this plan-edit turn.

## Review focus (tests required in owning tasks)

1. Attacker submits `amountCents=0`, `499`, fractional, too large, string, or extra currency => Task 1 returns 400 and never calls Stripe.
2. Host/Origin mismatch or a missing Stripe key => Tasks 1–2 fail closed, without leaking credentials or redirecting elsewhere; Origin spoofing by a script is **not** preventable with this check and is covered by rate limiting/Radar.
3. User reloads `?donation=success` or forges a valid-shaped unpaid/other-purpose session ID => Task 2/4 does not show paid confirmation.
4. Checkout fails, network drops, or a user double-clicks => Task 3 retains modal with a retryable error and sends at most one in-flight POST.
5. Non-German first locale and keyboard/mobile interaction => Task 3 renders English copy, cancel/close restores focus, and mobile modal fits viewport; native Escape/Tab behavior is checked in a real browser, not inferred from jsdom.

## Risks, tradeoffs, open questions

- **Legal/tax:** Marco says he operates a sole proprietorship; a payment supporting his household may have accounting/tax implications and is not automatically a charitable donation or deductible gift. Avoid charitable/tax-receipt language and have the updated legal/privacy text and payment classification reviewed before public live launch. Stripe business-account rules may require choosing an appropriate product description and business classification.
- **Product:** An inline `price_data.product_data` avoids up-front manual Product/Price setup and supports arbitrary validated amounts; it may create additional Stripe catalog objects and is less tidy than a fixed Price. If Stripe test-mode confirms catalog clutter or account restrictions, switch to one dedicated Product with inline `price_data[product]=prod_...`, add `STRIPE_DONATION_PRODUCT_ID` as a server-only binding and a test, **before** live rollout. Never create production objects on the strength of unit-test mocks.
- **Availability/security:** Public Pages and local Node are distinct runtimes. WAF/Turnstile + Stripe Radar are explicit **release gates**, not features provided by the Origin header. Some Cloudflare plans may not offer the specified rate-limit rule; if unavailable, implement and test server-verified Turnstile or keep the public flag off. The current static Pages preview cannot serve `/v1/convert` merely because donations start working.
- **Status without webhook:** Verifying a returned Checkout Session against Stripe is enough to avoid false paid confirmations. Delayed methods can yield `processing` long after returning and this no-webhook app cannot proactively notify the donor when payment settles; show a neutral message and direct them to Stripe's receipt/account, not an unconditional promise of email. No accounting reconciliation, receipts under our control, or persistent donation records; Stripe Dashboard remains the financial ledger. Add webhooks only if later requirements introduce fulfillment or durable records.
- **Locale:** The requested region behavior is approximated with browser locale; browsers can misreport region. Consider a manual language toggle later if users report wrong-language copy.
- **Source of Stripe token:** Exact key location, mode, and permissions are not yet verified in this repo. Before implementation/release, inspect presence/mode **without printing the key**, validate the key against the correct Stripe account in test mode, and never substitute the PDF `API_TOKEN` for Stripe credentials. Do not declare Stripe's approval of this use case without account-level evidence.
